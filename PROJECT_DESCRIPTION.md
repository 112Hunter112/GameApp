# DuoSport — Complete Project Description

A full-stack-ready backend for a sports platform that fuses **court booking**,
**social matchmaking**, **competitive match tracking**, and a **venue-owner
operations suite**. Two-person project, Spring Boot monolith,
PostgreSQL/PostGIS, ~104 automated tests.

> Accuracy note: this document was generated by reading the actual source, so
> it reflects what is *really* in the codebase (e.g. booking concurrency is
> handled by JPA pessimistic row locking, **not** Redisson — Redisson is a
> dependency but is not wired into application logic).

---

## 1. What the product is

DuoSport is two apps in one codebase, separated by role:

- **Players** discover nearby courts, book them by the hour, log match results
  against friends, build a per-sport **Elo rating** and a **reliability score**,
  showcase real-world **awards/trophies**, and get matched with players of
  similar skill nearby.
- **Venue owners ("hosts")** upgrade in-app to a management mode: approve
  bookings, set booking policies, block courts, and run an analytics dashboard
  (revenue, occupancy heatmap, no-show tracking, and "Smart Fill" — pinging
  nearby players to fill empty slots).

---

## 2. Architecture at a glance

- **Layered Spring Boot monolith:** Controller → Service → Repository, with
  DTOs at every boundary (entities are never serialized to clients).
- **Stateless JWT auth** so the app can scale horizontally.
- **PostgreSQL 15 + PostGIS** for relational data and geospatial queries.
- **~107 REST endpoints** across 15 controllers.
- **31 JPA entities**, **24 repositories** (incl. interface projections),
  **23 services**.
- **Role-based security** (`@PreAuthorize`) + per-resource ownership checks in
  the service layer (IDOR-proof).

## 3. Feature areas (everything that was built)

### A. Authentication & account security
- Email/password registration with a live-validated password policy.
- **JWT access tokens** + **rotating refresh tokens** — refresh tokens are
  **SHA-256 hashed at rest**, single-use, and rotate on every refresh;
  reuse of a rotated token is treated as theft and revokes all sessions.
- **Google OAuth2 sign-in** via server-side ID-token verification.
- **Forgot-password flow** with 6-digit codes (hashed, expiring,
  attempt-limited) emailed to the user.
- **Timing-safe login** (constant-time comparison to prevent user enumeration).
- **HaveIBeenPwned breach-password screening** (k-anonymity) per NIST 800-63B.
- "Become a host" role upgrade that re-issues a fresh JWT with the new role.
- "Log out of all devices."

### B. Geospatial venue discovery (PostGIS)
- Venues store a `geometry(Point, 4326)` location with a **GIST index**.
- Native queries with `ST_DWithin` (index-backed radius filter) +
  `ST_Distance` (ordering) return nearby venues/courts ranked by distance.
- Venue **search** (by name + optional location) and a personalized **home
  feed** that blends the user's sports, nearby venues, and recommendations.
- The home feed opportunistically refreshes the user's last-known location
  (best-effort) to power Smart Fill targeting.

### C. Court booking engine
- **Availability grid:** per-court, per-day time slots computed from the
  venue's booking policy (slot increment, min/max duration, advance window,
  opening hours), subtracting existing bookings and owner blocks.
- **Booking lifecycle** modeled on Airbnb's request/instant-book:
  `CONFIRMED` (instant) or `PENDING` (request) → owner approves/declines →
  either party cancels (bound by a cancellation cutoff) → lazily `COMPLETED`
  once the end time passes.
- **Double-booking prevention via JPA pessimistic locking** —
  `SELECT ... FOR UPDATE` on the court row before the overlap check, so
  concurrent `create()` calls serialize instead of racing.
- **Booking policies** per venue: slot size, min/max length, advance-booking
  window, minimum notice, cancellation cutoff, auto-confirm toggle, and JSONB
  opening hours.
- **Court blocks:** owners hold a court for maintenance / private events /
  league nights; blocked time rejects bookings exactly like a confirmed one.
- Notifications fire on create/confirm/decline/cancel to the right party.

### D. Match tracking & competition
- **Manual match logging:** pick sport, date, build Team A / Team B (friends
  by search, or external opponents by email invite), enter score, choose
  winner.
- **Two-party verification:** opponents must confirm a result before it counts;
  supports **dispute** and re-verification.
- **Match photos ("Memories"):** participants attach image URLs with captions;
  URL validated (HTTPS-only, SSRF-guarded against private/loopback hosts,
  optional host allow-list), capped per match, uploader-only delete.
- **Stats:** overall record, win %, streaks, monthly performance,
  head-to-head, most-played opponents.
- **Elo scaffolding:** per-sport rating fields, an idempotency guard
  (`ratings_applied`) so re-confirmation can't double-apply. (Rating math is a
  deliberate in-progress hook.)

### E. Awards / trophy cabinet
- Standalone real-world achievements (placement, competition, location, date,
  description) — not tied to a logged match — so users can showcase tournament
  wins and race placements.
- Award photos with the same hardened URL handling as match images, capped
  per award.

### F. Social graph
- Friend requests with optional message, accept/decline/cancel/unfriend,
  friend lists, suggestions, mutual-friend counts, user search.
- Notifications for friend requests and acceptances.

### G. Notifications
- Unified feed (paged DTOs, never raw entities), unread badge count,
  mark-all-read, typed notifications (friend, match, booking, Smart Fill,
  no-show) with deep-link reference IDs.

### H. Vendor / host operations suite
- **Owner overview:** cross-venue revenue rollup + per-venue breakdown.
- **Venue dashboard:** week/month revenue, today's bookings, 30-day no-shows &
  cancellations, upcoming schedule annotated with **player reliability tiers**,
  per-court utilization.
- **Occupancy heatmap:** hour-of-week grid (ISO day × hour) showing dead zones.
- **Revenue-left-on-the-table report:** priced empty hours per court.
- **Smart Fill:** notifies the *nearest* matchmaking-eligible players who play
  the sport and are available that day type, in one PostGIS query ordered by
  distance — with **per-court daily rate-limiting** and **dedup** (every offer
  recorded) to prevent spam.
- **No-show marking:** owner flags a no-show; player is **notified** (fairness)
  and it's timestamped for audit; feeds the network-wide reliability score.
- **Player reliability:** computed live from booking history (no-show rate →
  EXCELLENT/GOOD/FAIR/POOR/NEW tiers), batched to avoid N+1.
- **CSV export** of bookings for the owner's accounting.

## 4. Database design highlights

- **31 entities**, UUID primary keys throughout.
- **Composite-key join tables** via `@EmbeddedId` + `@MapsId`:
  `UserPreference` (user_id + sport_id) and `Participants` (match_id + user_id)
  — many-to-many *with attributes*.
- **One-to-one** Booking ↔ Match (a confirmed booking can yield a logged match).
- **PostGIS** `Point` geometry + GIST index for spatial search.
- **JSONB** for venue opening hours; `text[]` element-collections for amenities.
- **Enum-as-string** columns with DB CHECK constraints for booking/payment/
  match statuses (type safety at the DB layer).
- **Idempotency & audit** columns: `ratings_applied`, `no_show_marked_at`,
  `confirmed_at`, `cancelled_by`, `cancellation_reason`.
- Hashed-at-rest secrets: refresh tokens and password-reset codes store only
  SHA-256 hashes.
- Targeted indexes on hot paths (court+time for overlap, user for awards,
  offer dedup, etc.).

## 5. Security posture (OWASP ASVS-aligned)

- Centralized `@RestControllerAdvice` with a typed exception hierarchy mapped
  to correct HTTP codes; **no stack-trace or internal-message leakage**.
- **CORS allow-listing** (wildcard refused at boot), security headers
  (HSTS, CSP, frame-deny, nosniff, referrer-policy, permissions-policy).
- **Mass-assignment defense:** request DTOs expose only writable fields;
  Jackson rejects unknown properties.
- **IDOR-proof:** every mutation re-checks the JWT user owns the resource.
- Request-size and pagination caps; per-field `@Size` length limits.
- **SSRF guard** on user-supplied image URLs (HTTPS-only, private/metadata
  hosts blocked, optional allow-list).
- BCrypt password hashing; secrets via environment variables; production
  Docker Compose + Caddy reverse proxy with TLS.

## 6. Engineering practices

- **~104 automated tests** across 16 test classes — Mockito unit tests for
  logic + **Testcontainers** integration tests that spin up a real PostGIS
  container (no H2 fakery for spatial code).
- **GitHub Actions CI:** runs `mvn verify` (unit + integration) on every push
  and PR; scheduled OWASP dependency-check for CVEs.
- **Profile-gated data seeder** generates 100k+ realistic rows for performance
  testing and `EXPLAIN ANALYZE` index verification.
- **Git fork/PR collaboration** between two developers, including resolving
  multi-file merge conflicts when integrating two parallel feature tracks.
- OpenAPI/Swagger documentation; Bean Validation throughout.
